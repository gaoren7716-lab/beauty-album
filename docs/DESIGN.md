# 美人画册 · beauty-album

把「一个完整可复现的人物配方」压成一个三位编号，让人能像记住电话号码一样记住一个形象。

**80 个编号（原型段 48 + 全球段 32）· 40 个主题 · 8 种门类 · 4 种呈现模式 · 5 种平台方言。**

四根轴各取一个：**编号 × 主题 × 门类 × 模式 = 102,400 种组合**，
每种组合可输出 5 种平台方言（SD / MJ / FLUX / 自然语言 / GPT）= **512,000 份可直接复制的词面**。
（这两个数由界面现算，不是写在这里的 —— 任何一根轴补条目，它第二天就该变。）

敲 `041` 出词，敲 `AL-041 --theme TH-006` 出组图，敲「东古典·清」按名字也能找到。

**在线打开：** https://gaoren7716-lab.github.io/beauty-album/
（GitHub Pages 直接托管仓库根目录的 `index.html`，内容与本地完全一致。）
不想联网就把仓库整个下载下来，双击 `index.html` 一样能跑 —— 它是单文件的，没有任何外部依赖。

## 这是什么

一个**成品册**。它不解决「怎么拼一个人」，只解决一件更难的事：
**让一个复杂配方可以被记住、被复现、被长期复用。**

用户记不住「冷调白皙 + 深眼窝 + 高颅顶 + 直角肩 + 克制神情」，
但他记得住 041。所以本库的核心不是数据量，是**编号**：
短、能敲、能念、发布之后永不改变。

## 与「美人画册 提示词库」的分工

两者独立，**不互相 require**，可以各自单跑。

| | 美人画册 提示词库 | 美人画册（本库） |
| --- | --- | --- |
| 是什么 | 零件库 | 成品册 |
| 回答 | 「这个人怎么拼出来的」 | 「我记住的 041 号，配这个主题怎么出图」 |
| 单位 | 面（骨相 / 肤质 / …） | **编号**（一个已装配好的完整配方） |
| 操作 | 组合 · 变形 · 冲突裁决 | 记住 · 换主题 · 抽卡 |
| 记不记得住 | 不必记，`BF-001` 只解决「找到条目」 | **必须记**，这是本库存在的理由 |

一句话：提示词库的编码是给数据库用的，画册的编号是**给记忆用的**。
所以画册的所有入口都吃裸编号，界面上也只有一个大输入框。

## 四根轴，不是三根

```
编号 AL-   她是谁              内容 ─┐
主题 TH-   她在什么地方穿什么      内容 ├ 正交，互不覆盖
门类 MED-  这张图怎么画出来       画法 ┘
模式       成品有没有字、怎么排    版式
平台       给哪个模型、什么语法    方言
```

### 为什么补了「门类」这根轴

缺了它，「把这个人画成油画」「画成动漫」这两件事在本库里**根本表达不出来**：
主题只改服装与场景，模式只管要不要写字，八面全是「她长什么样」。
于是 48 条编号无论怎么配，出来永远是同一批照片味的写实人像。

这不是分类不够细，是**一个具体的能力缺失**。补上门类后，
同一个 AL-001 可以是照片、古典油画、工笔重彩、动漫赛璐璐、3D 渲染、游戏原画。

### 门类不改身份层的内容，只改它的表达方式

这是这一轴最容易做错的地方，也是体检里重点守的一条。

```
骨相「颅顶饱满偏高，颧骨外扩，下颌角内收成锐角」  ← 不变，换了就不是同一个人
肤质「哑光，毛孔细小但存在」                    ← 这是照片专属的表达
```

门类是赛璐璐时，肤质必须换成「肤色平涂无毛孔，明暗以块面区分」。
**不换的话，门类就只是一个贴在词尾的标签**——模型读到「照片质感」和「赛璐璐」
会各让一步，出来是「画风像照片的动漫人」，两边都不像。

所以 `MEDIUM_RULE.rewritable` 只允许改 `skin / eye / form` 三面，
改到骨相或气质（那是「她是谁」）或改到妆造、场景（那是主题的活），
`check_album` 直接报错。这条**反向验证过真会拦**。

### 门类的负面词负责压掉另一个门类的特征

`anime` 的负面词里有「油画笔触」「写实毛孔」「3D 渲染感」——
这些词漏了，出来就是画风串味。门类的 neg 排在模式 neg 之前就是这个道理。

### 门类之间会打架，但不拦

| 关系 | 判定 | 例子 |
| --- | --- | --- |
| `clash` | 两种画法直接冲突 | 油画 × 赛璐璐、3D × 油画 |
| `warn` | 能出图，但结果在两个画风之间 | 赛璐璐 × 半厚涂 |
| `ok` | 可自由组合 | 其余 |

**一律禁止是错的**——那等于把使用者逼回默认档，而「anime + semi」确实能出图。
写进 warns 说清代价，判断权交给使用者。

冲突表是手写的，所以查法是**双向匹配**而不是「排序后比对」：
早先的写法要求写表的人恰好按字母序写（`["oil","anime"]`），
违反的后果是 clash **静默降级成 ok**——规则失效但不报错。
这种没有提示的约定守不住。

### 门类也有画不出来的东西

`anime` 的 `caution`：「赛璐璐会把极端骨相磨圆——下颌角内收成锐角这种锐度，
在平涂里画不出来。配『冷调锐利』类编号时骨相损失最大。
**这是画法的限制，不是编号写错了。**」

不写这一条，使用者会以为是编号写坏了。

## 这个长文该学什么、不该学什么

外部给过一份《全球美人视觉图鉴》的八系统方案。评估结论：

**该学**：① 门类分层（本库已补成第四根轴）②「三个时代必须分开」——
人物生活的时代 / 作品描绘的时代 / 作品创作的时代，
本库的 `test` 类信息（写明在哪个模型上跑过）已经在做同一件事；
③ 未核实信息标「待核实」、不从画面风格反推作者与年代——
与本库 `fact / read / seen / test` 四分类同向。

**不该学**：那套 8 大系统 + 数十子目录的目录树。
理由是硬的——**这些维度是正交的，平铺成目录树等于强迫互斥**。
「唐代仕女图」同时属于中国传统 + 传统绘画 + 女性角色 + 齐胸襦裙 + 暖色侧光，
塞进一棵目录树就必须选一个，剩下全丢。**按目录查必然漏，按标签查才不漏**，
而这正是本库「编号 × 主题正交」已经解决的问题。

`06_AI创作与Prompt` 里那段「组合工作台」演示，长文自己也写了
「这只是组合逻辑的演示，不代表已接入实际图片数据库」——
那类东西在没有真实数据支撑时最容易变成看起来很完整的空壳。

## 核心：正交两轴

### 身份层与可变层

```
编号（AL-）→ 骨相 · 肤质 · 眼目 · 形体 · 气质    恒定 —— 这是「这个人是谁」
主题（TH-）→ 妆造 · 场景（+ 发型可覆盖）        可变 —— 这是「画什么」
```

这是本库唯一真正的新东西，比它的编号数量更有价值：
**固定 041 号 + 换十个主题 = 十张风格一致、内容不同的图。**
反过来，固定主题换编号 = 一次试十种画风。

### 为什么这样切

分界线是**「这个人的产物」还是「时代与处境的产物」**：

- 骨相、肤质、眼目、形体、气质 —— 换任何一个，都不再是她。年龄会变、体型会变，
  但这些东西是这个人**本身**。
- 妆造、场景 —— 是「她在什么年代、什么地方、什么处境」的产物。
  同一个骨相可以是民国的学生，也可以是赛博的技师，这两件事不矛盾。

### 为什么身份层必须恒定

**如果主题能改骨相，那记住编号就没有意义了 —— 你记住的「041」就不再是 041。**

这是全库的立身之本，所以 `check_album.js` 里有专门一组断言（第 6b 组）：
取 6 个跨类目的编号 × 4 个主题，把身份层五面拼成字符串，
**要求所有组合下的结果逐字相同**。只要有一种不同就报错：

> `AL-041 的身份层随主题漂移（2 种不同结果）—— 记住编号就失去意义了`

这条断言要拦的是一个**界面上完全看不出来**的问题：
图照样出得来，只是两次出的不是同一个人。

### 为什么场景这一面编号不提供

**画册管人，不管景。**

场景是内容的容器，它由主题决定。而如果编号也带场景，
「固定编号换主题」就会在编号的旧场景和主题的新场景之间打架 ——
表现为「赛博义体 + 清晨通勤」这种组合悄悄带上海滩。

所以编号条目里**没有 `scene` 面**（全球段按同约执行，编号里 `scene` 出现 0 次，这是设计不是漏写）。
不给主题时它就空着，并在 `warns` 里明确报出来：
**留空 + 明确警告，比悄悄继承一个与主题无关的旧场景强。**

### 发型的特殊位置

发型放在「可变」这一侧，但它同时是**身份的一部分**：

| 写法 | 语义 |
| --- | --- |
| `mutable: "soft"`（`hair`） | 主题指定了发型就覆盖，没指定就保留编号里的 |
| `mutable: true`（`dress` / `scene`） | 主题指定就覆盖，没指定就留空并报出来 |

为什么发型是 soft：它常随时代与场合变（民国髻 / 现代高马尾），
但编号里总有默认发型，主题没提就说明「这一号的发型挺好，用它」。
而妆造与场景没有这个默认值 —— 编号里的日常装配「清晨通勤」会打架。

## 姓名不进提示词（先读这一节）

**真名只出现在 `zh` / `en` / `alias` / `namedRef` 里，用于查找与指代，永远不进提示词。**

这不是「加个开关然后默认关掉」，是**根本不给开关**
（`NAME_POLICY.emitNames` 硬编码为 `false`）。三个理由与提示词库相同
（不能免责 / 不稳定 / 不可组合），但**画册层更要强调第一条**：

> **编号会被长期复用。一个编号里藏了人名，等于这个编号每次用都在漏。**

提示词库的条目可能只用一次，而画册的 041 号会被反复用在一百张图上。
所以画册的姓名纪律比零件库更硬：编号是**长期资产**，泄漏是**累积的**。

主要手段是数据里根本不写名字（当前 48 条全部是原创抽取，`namedRef` 只有 1 条，
内容还是「（群像类型，非特定真人）」）。引擎的 `stripNames` 只是**第二道防线**。

（这道防线早先有一处误伤：它把条目自己的描述性名字也当真人名剥掉了。
已修 —— 现在只剥 `namedRef` 这一个字段，见「已修的三条」①。）

## 授权四档

分级口径只有一条：**只看是否指向可识别的真人，不看画法。**

| 档 | 中文 | 能否用 | 含义 |
| --- | --- | --- | --- |
| `R0` | 自由 | 可直接商用 | 形象为原创抽取或公有领域传统，不指向任何可识别的在世真人 |
| `R1` | 署名 | 可商用，建议署来源 | 原型已故或形象已进入公有领域，但风格有可识别归属 |
| `R2` | 仅参考 | 先改写特征再商用 | 特征组合与某位在世真人高度相似，需自行评估肖像边界 |
| `R3` | 改写后用 | 必须改写特征后使用 | 原型可考据且在世，或原型为具体作品角色 |

**最高档不是禁用，是「必须改写后使用」。**
理由是「像某位明星那样画」与「画一个高颅顶长颅的女人」法律上完全不同 ——
前者指向具体的人，后者是一组物理描述。

### 为什么画册每条都必须显式标档

编号 = 一个完整人物配方，而**完整配方里必然带着一组能拼回某个人的特征组合**。
所以每条编号都显式标档，连 `R0` 也要写 —— 没标 = 没评估过。

标 `R3` 不影响使用，只影响发布。

### 当前授权分布

| 档 | 条数 | 占比 |
| --- | --- | --- |
| `R0` | 48 | 100% |
| `R1` | 0 | 0% |
| `R2` | 0 | 0% |
| `R3` | 0 | 0% |

**R1 / R2 / R3 三档目前为 0 覆盖。**这不是遗漏，是当前的诚实状态：
48 条全部是原创抽取的形象，没有一条指向可考据的在世真人。
`RIGHTS.inspect()` 的多档取严逻辑已经写好并可测，但**没有真实数据喂给它**。

`RIGHTS` / `PROVENANCE` / `TESTS` 三张登记表当前均为 0 条（见「覆盖缺口」）。

## 风险标注

风险与授权是**两回事**：授权管「能不能发」，风险管「产出像不像某个真人」。

| 风险 | 中文 | 当前条数 | 含义 |
| --- | --- | --- | --- |
| `none` | 无特别风险 | 48 | 形象为原创抽取或公有领域传统 |
| `lookalike` | 形似风险 | 0 | 特征组合可能与某位真人高度相似，产出前需自查 |
| `identity` | 身份指认风险 | 0 | 原型可考据且在世。真名只作查证与指代 |
| `sensitive` | 敏感属性风险 | 0 | 涉及年龄、体型、族裔等敏感维度 |

与提示词库相比，画册多一层考虑：**编号比单条描述更容易被传播**。
「041 号风格」会被反复用在一百张图上，所以**编号级的风险比单条条目更值得盯**。

引擎在 `compose()` 输出里带 `warns` 段，`show_plate.js` 与界面都必须显式报出来 ——
一条被默默使用的风险提示等于没有提示。

## 网页结构：主用平铺，低频收进「更多」

双击 `index.html`。顶部页签分两组 —— **主用 4 个平铺，低频 4 个收进「更多」下拉**。
8 个平铺时，小白第一眼要处理 8 个决定，而其中 4 个是低频操作；
分组后主干道上只有一条路：**看图 → 点开 → 复制**。

| 页签 | 干什么 | 关键操作 |
| --- | --- | --- |
| **画廊**（默认） | 80 张卡片，看图选人 | 点卡片看详情+一键复制；点图看原图。复制参数默认折叠成一行「复制配置：TH-001 · 实拍 · 纯图 · GPT ▾」，点开才改 |
| **一句话出图** | 说一句想要什么 → 自动配编号与主题 → 直接复制 | 手选编号同样**网格卡多行多列**（按段折叠）；页内自选门类/模式/画幅；**主题由一句话自动配，不用手选** |
| **抽卡** | 随机组合，铺 8 组 | **不用先选任何东西**，点「抽」就行；每张可锁住某轴只换其余；「用这组」送精品出图 |
| **精品出图** | 编号 × 主题 × 门类逐项手选，实时出词 | **主题的完整选择在这里**（40 个分组排列）；轴一 80 条**网格卡多行多列**（按段折叠：当前选中常显、所在段自动展开、选完收起）；五平台语法切换 |
| **组图** | 一个编号 × 多个主题 | 勾选，或按类目全量 sweep |
| **体检** | 检查+治理**每次打开现跑一遍** | 覆盖矩阵 + 地域覆盖 + 已知缺口 + 冲突裁决 + **授权与姓名策略（已并入）** |

### 轴控件跟着消费方走，不再全局常驻

四根轴曾经全局常驻顶栏，但**一半页面根本不消费它们**：
一句话出图的主题是一句话自动配的（全局主题与它无关）、
抽卡的主题是随机抽的（选了主题就只剩两根轴可随机）。
「不生效却显示着」的回显是在撒谎。所以撤销全局轴条，
每个页面只显示自己真正消费的轴：

| 页面 | 主题从哪来 | 门类/模式/平台 |
| --- | --- | --- |
| 画廊 | 页内「复制配置」（默认折叠） | 同左，折叠态一行回显 |
| 一句话出图 | **一句话自动配** | 页内自选（门类独立 cMedium） |
| 抽卡 | **随机抽**（可锁） | 随机（可锁） |
| 精品出图 | 页内 40 张网格卡手选 | 页内手选 |
| 组图 | 勾选多个 | 页内手选 |

命名沿革：两轴工作台 → 精调出词 → **精品出图**（用户定名）；
自定义出图 → 一句话出词 → **一句话出图**（用户定名）。

**已下线/合并的页**：
- 「更多 ▾」下拉整体撤销 —— 事实是没人点开它，下拉里的东西等于不存在。
- **词条库下线**：编号词条 → 画廊卡片与详情浮层；主题/模式词条 → 精品出图页。
  渲染代码已删，冒烟里有「替代覆盖」断言防丢失。
- **授权合规并入体检页**（rightsBody 复用，rights 视图直达入口保留）。

**全局轴条也做了同一件事**：默认只露「主题」一根轴，
画法/成品/语法收进「高级」按钮 —— 多数人复制提示词只换主题，
把四组全平铺等于让 90% 的人为 10% 的进阶功能多付三次注意力。
展开状态在当前视图内保留，切页不清。

**为什么是「顶部页签 + 一栏全宽」而不是三栏**：三栏时主区被压到 430px，
80 张卡片一屏只放得下几张，而画廊的全部价值就是「一眼扫过去」。
详情改成浮层 —— 它是要细读的内容，浮层给它整块宽度。

### 画廊一键复制：复制的到底是什么

48 张卡片每张都有两个按钮：**复制提示词**（正面词）+ **负面词 N**。
点开卡片后的详情浮层里还有一份，看完八面可以直接复制，不用退回网格找卡。

「复制提示词」给的是 **该编号 × 当前主题 × 当前模式 × 当前平台**，不是纯编号。

纯编号不能单独出图：`scene`（场景）面由主题给，裸编号合成出来会缺这一面
（`compose("AL-001", {themeId:null})` 的 `missing` 里就带着 `scene`）。
所以按钮必须带上主题 —— 但**带上就必须在卡片上写明是哪两轴**，
只写「复制」的话，使用者拿到一条词却不知道它掺了什么。

**这三个状态原本住在工作台里，画廊页看不见也改不了**，
所以顶栏有一条「出图三轴」条（主题下拉 + 4 个模式 + 5 个平台）：
看不见的依赖等于界面在骗人 —— 你在工作台切了 FLUX 再回画廊，
每张卡复制出来的都是你看不见的那套配置。

这条三轴条**是全局的，不属于画廊**。它放在画廊内部会让人以为
「这三根轴只管这一页」，而工作台的主题与模式、组图的模式、
抽卡的模式、自定义页的平台全部跟着同一份 `S` 走 ——
**控件所在的位置不该比它的作用域更窄**。所以它现在挂在顶栏，
八页都在。

条末有一行实时回显「此刻：GPT · TH-001 清晨通勤 · 纯图」。
没有它，这一行就只是三个控件：切完看不见切成了什么，
而复制出去的是切完之后的结果 —— 控件与结果之间断一环，用的人就得靠猜。

**默认平台是 GPT**（用户 2026-10-11 指定）：GPT 图像这类对话式模型
现在是最常见的出图入口，默认落在 SD 上等于让多数人一进来就在改平台。

### 复制失败时，界面会说自己失败

`navigator.clipboard.writeText()` 返回的是 **Promise**，「调用了」不等于「写进去了」。
Firefox 在 `file://` 下 clipboard 是存在的、但写入会被拒；
此时如果照旧弹一句「已复制」，用户看到的是成功、剪贴板里是空的，
而且**没有任何东西会报错**（没人接的 rejection 静悄悄丢掉）——
这种失败最坏的地方在于没有症状，它会一直被当成模型的问题。

所以 `copyText()` 三条路走完才说话：

| 情况 | 结果 |
| --- | --- |
| clipboard 写入成功 | 报「已复制 AL-002 × TH-001 · 纯图 · SD（322 字）」 |
| 被拒 / 不存在 | 回落 `execCommand`（双击 `index.html` 的真实路径），成功就报成功 |
| 两条都失败 | **不谎报**，弹「手动复制」框，全文已摊开并全选好，按 Ctrl+C 即可 |

第三条不是多余的：那条 322 字的词是现算出来的，界面上本来没有它的全文，
只提示「复制失败，请手动复制」等于让人手打 322 个字。

`smoke_ui.js` 的 A10 组对这四条路径各测一遍，且**每个用例独立装载一个窗口** ——
四种浏览器环境要改写 `navigator.clipboard` 与 `document.execCommand`，
共用一个窗口的话第三个用例拿到的已经是第二个留下的现场，
断言红了也分不清是功能坏了还是前一个用例没收拾干净。

### 为什么负面词单独一个按钮

正面词与负面词**不能拼成一条**。拼在一起，SD 用户粘进 Positive 框
就把「不要文字」写成了「要文字」，而纯图模式的负面词第一条正是「文字」。
反过来只给正面词也不行：没有负面词的纯图模式，模型几乎必然会自己加字。

所以两串分开给，各自可复制：

| 出口 | 负面词怎么给 |
| --- | --- |
| 画廊卡片 / 详情浮层 | 「负面词 N」按钮，N 是条数（写在按钮上，不用点了才知道有没有） |
| 精品出图 | 负面词区末尾「复制负面词」（红色按钮） |
| 自定义出图 | 同上，取的是这一页自己的模式（`cMode`，不是全局 `mode`） |
| 抽卡 | 单卡「负面词」按钮取**那一组自己抽到的**模式；「一键复制全部」逐组附带 |
| MJ 平台 | 自动带 `--no` 前缀（给裸词，用户粘进 MJ 就成正面词了） |

**抽卡单组的负面词不能拿编号去现算**：那算的是全局主题/模式，
跟这一组抽到的不是一回事。错配最典型的后果是图文组的「不要文字」
被加到纯图组，模型照样加字。

### 自定义出图为什么不出图

本库是「双击就能用」的离线库，不联网、不装密钥。
真出图要密钥，一旦要密钥这个库就不是离线的了。
所以这一页的产出是**一条可以直接贴进任何生图模型的提示词**，不是一张图。

三条纪律：

1. **原话是追加，不是覆盖。** 它拼在词面末尾，不参与冲突裁决 ——
   参与裁决的话，「我要一张悲伤的图」就会去改骨相，而那是身份层。
2. **自动配必须给出命中了什么词。** 只给结果不给理由，用户无法判断该不该信；
   而猜错的推荐被照抄，比没有推荐更糟。
3. **没命中就直说没命中**，不偷偷给随机结果。
   降级到二字滑窗的宽松匹配时也要标出来 —— 滑窗会切出「红机」「械义」
   这类跨越词界的碎片，命中数看着有，不代表真的对得上。

### 抽卡的锁与重抽

每张抽到的卡下面有三个锁、四个重抽：**换编号 / 换主题 / 换模式 / 整组重抽**。

只有「全部重抽」的话，抽十次也碰不到「同一个人换场景」的对比 ——
而那正是画册最想让人看到的东西。

「只换一个轴」的实现是**整组重抽一次，再把不动的轴回填**，
不是「只对那一轴重新随机」：主题要过语义护栏，
而护栏判的是「这个编号配这个主题」，单独换主题就绕过了它，
抽出来的可能正是被挡掉的那类组合。

## 三种玩法

### 一、直接用编号（敲号出词）

```bash
node tools/show_plate.js 001
node tools/show_plate.js AL-041 --theme TH-006 --mode graphic
node tools/show_plate.js 霜白刀刃              # 中文名 / 英文名也吃
```

按三层显示：**编号本体**（八面 + 授权 + 风险 + 用法说明）
→ **组合结果**（五平台 tags + neg + 正文）
→ **授权与风险**。

分三层的理由：这三层的读者不同。第三层是唯一有法律后果的一层，
合成一屏的话使用者会把它当脚注。

### 二、一号出组图（sweep）

固定一个编号，铺开全部 40 个主题 —— **当前画册最常见的用法**：

```js
GACHA.sweep(db, "AL-001")   // → 40 组，每组都是同一个人、不同内容
```

为什么这是真实需求：画册的用法是「我要一组图」，不是「我要一张图」。
逐个调 `compose` 太碎。

### 三、抽卡（roll）

从库存里随机抽一组（编号 × 主题 × 模式），一次铺开 8 组（界面默认 8）。

```js
GACHA.roll(db)                                  // 抽一组
GACHA.roll(db, { seed: 42 })                    // 可复现：同 seed 必同结果
GACHA.rollMany(db, 8, { seed: 42 })             // 连抽 8 组铺开
```

抽卡**不是「同一提示词换 seed」** —— 那是同一张图看六遍。
本库是**每个轴各抽一条**，所以抽出来的确实是没见过的组合。

组合空间 **102400**（80 × 40 × 8 门类 × 4 模式，四维全乘），每次现算、不缓存：
缓存下来就会在库升级后显示一个旧数字，而「数字停在旧规模上」看起来完全正常，只是它在说谎。

`seed` 可复现是硬要求 —— 抽卡结果会被分享（「按这组抽的」），
不可复现就等于没法交流。随机数用 mulberry32，不用 `Math.random`。

## 抽卡的语义护栏

编号与主题是两根**独立随机**的轴，独立抽就会抽出「少年感 + 手术室」
「古典 + 赛博义体」这类**语义上打架**的组合。

> **这类失败不报错。** 抽卡不会说「这一组不合理」，
> 它只会给你一张奇怪的结果图，而用户多半以为是自己主题选得怪。

所以候选上带语义标签（`cat` / `age` / `mood`），抽之前先筛。

### ★ 第一版护栏是空的

第一版按「推断出的 `age` 档位差 ≥ 2 就挡」。实测：

> **1920 种组合里，挡掉 0 个。**

因为所有类目都被推断成 `young` 或 `adult`，档位差最多是 1。
**护栏看着在，实际上是空的。**

教训：**判据必须落在真实的语义差异上，而不是我推断出来的数值。**
推断是我编的映射，类目冲突是内容里本来就有的事实。

### 现在的判据：按类目对

`CAT_CLASH` 直接列出哪两个类目天然打架：

| 编号类目 | 进不了的主题类目 | 为什么 |
| --- | --- | --- |
| `少年感` | `职场身份` | 一个看着十四五岁的人做主刀或出庭，读者第一反应都是「不对」 |
| `古典` | `幻想设定` / `都市日常` / `职场身份` | 题材的时代性是硬约束，东古典发髻配义体接口，观感上直接崩 |
| `明艳` | `文艺古典` | 高对比高饱和的现代妆配素雅古装，气质对不上 |

当前挡掉 **216 / 1920（11.3%）**，并把被挡数量作为 `semanticBlocked` 报出来 ——
「7680 种组合」听起来很多，但实际可抽的受语义约束，只报总数会让人高估抽卡空间。

规则刻意保守：**只挡确实荒谬的组合**。判据太严会让抽卡退化成「只能抽到安全组合」，
那和没抽卡一样 —— 抽卡的意义就是看到没见过的搭配。

被挡掉的候选会带上原因（`clashReason`），
因为**一条不解释的抽卡结果只会让人以为是随机噪声，而它其实是规则**。

`opt.semanticOff` 可以显式关掉护栏（要「完全随机」时用）。

## 编号编排约定

**编号是给记忆用的，不是给数据库用的。**四条硬约定：

1. **两段编排：原型段 + 全球段。**
   - **原型段 001–048**：不锚定地域的抽象审美类型
     （001–008 冷调锐利、009–016 暖调柔和、017–024 中性硬朗、
     025–032 少年感、033–040 明艳、041–048 古典）。
     相邻编号落在同一气质区，翻到 030 一带就知道在找什么。
     **它们的骨相基线是东亚审美** —— 这一点如实标注，不伪装成全球分布。
   - **全球段 049 起**：按文化圈分段，每圈 4 条起步、目标 8 条，
     圈内相邻编号同圈。
     `049–052 东亚汉文化圈 · 053–056 东南亚 · 057–060 南亚 ·
     061–064 西亚与北非 · 065–068 非洲 · 069–072 欧洲 ·
     073–076 美洲 · 077–080 大洋洲`。
   两段是并行的两种用法：要「不限地域的类型」用原型段，
   要「具体文化圈的人」用全球段。画廊有「全球段」一键筛选。

2. **编号一旦发布永不改。**改了等于让用户手里的「041」失效。
   新增只往后追加，不重排。全球段的扩圈（每圈 4 → 8 条）
   也从 081 往后排圈号，不插入既有段。

3. **缺号是已删除，别复用。**
   当前 `AL-001 ~ AL-080` 与 `TH-001 ~ TH-040` **均无缺号**。
   将来删掉某条后，那个号就空着 —— 让「已删号」不被后来的人重新启用，
   否则一个曾经指向某个形象的号会悄悄变成另一个形象。

4. **每条全球段必须带 `region`（文化圈）与 `culture`（具体文化）。**
   只有编号没有地域，全球段就退化成一堆空壳 ——
   体检页的地域覆盖表按它现算，画廊的地域筛选按它过滤。

5. **类目表单独声明，不由数据现算。**
   六类与八圈写在 `assets/data-core.js` 的 `ALBUM_TAXO`，
   主题八类写在 `THEME_TAXO`。界面分组**按声明顺序**，
   不按「数据里首次出现的顺序」—— 后者等于把
   「001 为什么是冷调锐利」这条编排决定藏进了文件行序，
   谁在数据中间插一条，整张分组表的顺序就跟着变，还不报任何错。

   两条轴正交，别混成一张表：

   | 字段 | 是什么 | 用在哪 |
   | --- | --- | --- |
   | `cat` | 气质区（六类，跨地域通用） | 原型段的分组键、抽卡语义护栏、色卡基调 |
   | `region` | 文化圈（八圈，全球段专用） | 全球段的分组键、画廊地域筛选 |
   | `culture` | 圈内细类（唐 / 波斯 / 毛利…） | 全球段卡面右上角小标 |

   三条硬规矩由 `check_album.js` 第 9 组守住：
   类目值必须在册（拼错一个字 = 从所有分组里消失）、
   同类的编号必须**连续成块**、主题类目同样连续成块。

## 姓名与编号的关系

编号的 `zh` 是**特征化命名**，不是真名：「霜白刀刃」「静水」「鹤骨」「东古典·清」。

命名规则是「抓这一号最显眼的那一点」：削 → 霜白刀刃，静 → 静水，长颅 → 鹤骨。
这样扫一眼画册就能想起这一号大概是什么，而不用读完七面。

### 画廊怎么展示图

配图是从 1 张补到 48 张的**过程**，所以「看」与「扫」两个用途都要能达成：

| | 用途 | 规格 |
| --- | --- | --- |
| **看图**（默认） | 判断骨相、看清妆造 | 卡宽 300px，图区 **360px**（接近 4:5） |
| **扫编号** | 一屏塞满 48 个号，靠编号认人 | 卡宽 196px，图区 104px |

**为什么是竖比例而不是横条**：出图是 1024×1536 竖构图，
用 1.9:1 的横条去 `cover`，裁掉的一定是额头和下巴 ——
也就是判断骨相最要看的那两处。`object-position: 50% 22%` 把取景锚在上三分之一，
因为人像竖图的脸通常在上半部，锚在中间会切额头。

**两档都留着**，因为 48 张里目前只有 1 张配图 ——
只留「看图」档的话，那 47 张色卡会被撑到比图还大，很怪。

**「只看有图」筛选**：配图覆盖率是这个库当前最该被看见的进度，
而没有这个筛选，使用者只能靠翻页面去找「哪几条已经有图」。
数量从 `test.pic` **现数**——写死的进度下个月就开始骗人。

**点图放大，点卡片看详情**——两个动作分开。
卡片里再怎么放大也是缩略图，判断骨相必须看原图。
放大浮层里除了原图，还给出这条的 `test` 记录：
出图模型、对上了什么、没对上什么。
**因为一张没写清来历的示例图，最容易被当成「就是这个配方出来的」**，
而它可能只是配图时挑了某个主题、某些面根本没在这张上出现
（AL-001 的 `dress` 面就被 TH-001 的米色风衣覆盖了）。

悬停边框的判据是 `:not(:has(.nopic))` 而不是「有没有 `<img>`」——
47 张没配图的卡里也挂着 `<img>`（等着哪天补图），`onerror` 才是「确实没图」的唯一证据。

### 配图：文件名 = 编号

画廊按 `examples/<编号>.png` 认图，**文件名必须等于编号**，扩展名 png / jpg 都行。
命名体例与 `anime-prompt-library/gallery-naming.md` 一致 ——
同一个 id 在两个库里指的是同一种东西。待配清单与补图步骤见 `gallery-naming.md`。

界面给**每张**卡都挂一个 `<img>`，命中与否交给 `onerror` 回落色卡。
反着做（只给有图的挂）的话，没图的卡就永远没有回落机会，
补图之后还要改渲染代码。

**离线页面读不到文件系统**，所以「有几张图」的唯一依据是数据里的 `test.pic` 声明 ——
而声明可以撒谎（图删了、挪了、改名了，数据里还写着它）。
`check_album.js` 对这条做了双向对拍：声明有文件没有 → 错，
文件有没有声明 → 警，文件名不是三位编号 → 错。三条都**反向验证过真会拦**。

## 已修的三条（留档）

以下三条曾是本库**真实存在**的问题，**现均已修复**。
留档不删，是因为它们的成因（裸全局作用域 / 数据里没有真名键 / 同一处推两次）
在这个库里随时会以别的面貌重来一遍。

保留它们的另一个理由：**文档说「还没修」而代码其实已经修了**时，
使用者会照着旧描述去绕一个已经不存在的坑 —— 那比不写更糟。
所以状态表必须跟着代码走。

| # | 问题 | 状态 | 现在的行为 |
| --- | --- | --- | --- |
| ① | `stripNames` 剥掉条目自己的名字 | **已修** | 只剥 `namedRef`；`TH-006 旧戏台` 的场景面完整输出 |
| ② | `rights.js` 的 `tierInfo()` 在 Node 下静默降级 | **已修** | 走容器 `_RC.RIGHT_TIERS`，浏览器与 Node 同结果 |
| ③ | 无主题时 `missing` 报同一个面两次 | **已修** | `compose(db,"AL-001",{})` 的 missing 只有一条 `scene` |

### ① ★ `stripNames` 会剥掉条目自己的名字（影响出图内容）

`album-kit.js` 的 `stripNames(str, obj)` 把 `obj` 的 `zh` / `en` / `alias`
一律当真人姓名剥掉。但**编号名与主题名是描述性命名，不是真人姓名**：

| 条目 | 原文 | 实际输出 |
| --- | --- | --- |
| `TH-006 旧戏台` · scene | `旧戏台，红幕布两侧垂落…` | `，红幕布两侧垂落…` |
| `TH-018 手术室` · scene | `手术室，无影灯冷白光…` | `，无影灯冷白光…` |
| `AL-012 米白` · dress | `米白色柔软质地衣物…` | `色柔软质地衣物…` |
| `AL-045 书卷` · aura | `气质书卷气` | `气质气` |

**影响范围：主题面 15 / 93，编号可投放字段 4 处，共 19 处。**

最严重的不是词面被削短，而是 `TH-006` 的场景**以一个逗号开头** ——
这**曾**直接进最终提示词。`check_album.js` 拦不住它（那一条查的是「真人名是否泄漏」，
而这里恰好是**反方向**：合法的描述性文字被当成名字剥掉了）。

**修法**：`NAME_KEYS` 从「`zh`/`en`/`alias` 一律当真名」改成
**只认 `namedRef` 一个键**，并在剥完后清掉首尾残留的标点
（否则「旧戏台」被剥掉后会留下一个以逗号开头的残句）。

两个候选改法里选了改引擎这一个：改 15 条数据也能避开，
但那会让主题名变得别扭，而且下次有人给条目起名时还会再踩一次。
真名与本库描述名的区分只能靠「哪个字段装的是真名」，
不能靠「这个名字看起来像不像人名」。

### ② `rights.js` 的 `tierInfo()` 在 Node 下静默降级

`rights.js` 里读的是**裸全局** `RIGHT_TIERS`：

```js
var tiers = (typeof RIGHT_TIERS !== "undefined" ? RIGHT_TIERS : []);
```

浏览器里 `data-core.js` 是 `<script>` 顶层的 `var`，全局可见，取得到；
Node 里每个文件是独立模块作用域，**那个全局不存在** ——
于是 `tierInfo()` 返回 `{ zh:"R0", can:"", desc:"" }`，
正好把「这一档能不能商用」这个最该显示的信息显示成空，
而**空字符串在终端上看起来和「没有限制」一模一样**。

`RIGHTS.inspect()` 不受影响（它有一份硬编码的 `can` 映射），所以 `compose()` 的输出是对的。

**修法**：`rights.js` 顶部建一个容器 `_RC`（浏览器取 `window`、Node 取 `require`），
`tierInfo()` 只从容器取 `RIGHT_TIERS`。
界面侧的同类问题同样处理：所有全局符号走 `need()` 取值并显式报错，
不写 `typeof X !== "undefined"` 那种「拿不到就当没有」的判断 ——
「空」与「无限制」在界面上长得一模一样，这是②这类 bug 最难查的地方。

### ③ 无主题时 `missing` 报同一个面两次

`compose(db, "AL-001", {})` 的 `missing` 里 `scene` 出现两次
（一次带 `reason`，一次不带）—— `album-kit.js` 里两处各推了一次。
**现已合并为一处**：当前输出只有 `[{face:"scene",zh:"场景"}]`。

它不影响出图内容（`faces.scene` 仍然是空的），
但按面统计时会虚高一格 —— 而体检页的「缺几面」正是按这个数算的。

## 关于图像与许可

本库的**代码与原创提示词**是本库的。

但**肖像与形象不是** —— 代码许可**不覆盖**数据表里的条目。
当前 48 条全部为原创抽取（`rights:"R0"`），每条 `fact` 里写明「形象为原创抽取，
不指向任何可识别真人」。

授权判定输出里必带这句：**「本判定为本库内部工程分级，不构成法律意见；商用前请自行复核」**。
内部分级是工程判断，不是法务结论 —— 这句话不能省。
